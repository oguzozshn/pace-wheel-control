## USB interfaces

The device is a USB composite device with two interfaces. Windows splits MI_01 into two
top-level collections, so there are three HID nodes:

| Node | Top-level usage | Max report lengths (in/out/feature, incl. ID byte) | Opens from user mode |
| --- | --- | --- | --- |
| MI_00 | Generic Desktop / Joystick | 21 / 18 / 5 | yes (shared) |
| MI_01 COL01 | Generic Desktop / Keyboard | 9 / 2 / 0 | no (Windows owns keyboards) |
| MI_01 COL02 | Generic Desktop / Mouse | 9 / 0 / 0 | no (Windows owns mice) |

### MI_00: game controller + force feedback

- Input report 0x01 (joystick):
  - X and Y: 16-bit signed, logical range -32767..32767
  - Z, Rx, Ry, Rz, Slider: 16-bit, 0..65535
  - one hat switch, 1..8 (8 directions)
  - 24 buttons, followed by constant padding
- Input report 0x02: PID State Report (device paused, actuators enabled, safety switch,
  actuator power, effect playing + effect block index).
- A complete USB HID PID 1.0 force feedback implementation:
  - output reports 0x01-0x08 and 0x0A-0x0E (Set Effect, Envelope, Condition, Periodic,
    Constant, Ramp, Custom Force Data, Download Force Sample, Effect Operation, Block Free,
    Device Control, Device Gain, Set Custom Force)
  - feature reports 0x05 (Create New Effect), 0x06 (Block Load) and 0x07 (PID Pool)
  - Effect Block Index 1..14, so up to 14 effects can be stored on the device
  - 12 effect types declared: constant, ramp, square, sine, triangle, sawtooth up/down,
    spring, damper, inertia, friction, custom
- There are no vendor-defined usage pages and no non-PID feature reports on this interface.

### MI_01: keyboard + mouse emulation, not a configuration channel

- COL01 Keyboard, report 0x01: 8 modifier bits plus 56 constant bits in, 5 LED bits out.
  No key array shows up in the rebuilt descriptor.
- COL02 Mouse, report 0x02: 15 buttons, plus relative X, Y and wheel (16-bit).
- **No feature reports and no vendor-defined usages.** Going by the descriptor, MI_01 is a
  keyboard/mouse emulation interface (probably for console or mobile modes), not the vendor
  configuration channel we hoped for in the plan.
- Windows opens keyboard and mouse collections exclusively for itself, so user-mode tools
  can't read their input reports. That's expected, not a bug in this tool.

Implication for Phase 4: the HID descriptors declare no place for vendor configuration.
Where the mobile app's settings go is still unknown. The candidates:
1. undeclared report IDs on MI_00 (Windows' HID stack rejects report IDs not in the
   descriptor, so these would only be visible in a USB capture), or
2. a different transport, for example Bluetooth, if the mobile app doesn't talk over USB.

A USBPcap capture is the only way to tell.

### Descriptor caveat

Windows does not expose the original report descriptor bytes. HidSharp rebuilds a descriptor
from the preparsed data, so:
- Item order, item encoding and Report ID placement differ from the firmware's descriptor.
  For example, values like `26 FF FF` stand for 65535, not -1.
- **Every report of one type is padded to that type's maximum length.** All output reports
  show 17 bytes and both input reports show 20, so per-report sizes in the dump are upper
  bounds, not real sizes.
- To get the true descriptor bytes, capture the enumeration with USBPcap
  (GET_DESCRIPTOR, HID report descriptor).

## DirectInput view

- Force feedback goes through the Windows HID PID class driver
  (FFB driver GUID `eec6993a-b3fd-11d2-a916-00c04fb98638`). There is no vendor FFB driver.
- Capabilities: 7 axes, 24 buttons, 1 POV.
  - Flags: `Attached, Emulated, ForceFeedback, ForwardFeedbackAttack, ForceFeedbackDate, Saturation, DeadBand`
- Both X and Y are flagged as FFB actuators. This is typical for PID wheels; only X is
  physically driven.
- All axes report DirectInput's default range 0..65535, with deadzone 0 and saturation 10000.
- With no application holding the device, DIPROP_FFGAIN = 10000 (100%) and DIPROP_AUTOCENTER = on.
  This is the baseline for the Phase 2 persistence tests.
- The FFB sample period and minimum time resolution are both reported as 1,000,000 µs. That
  looks like a placeholder value from the PID driver, not a real device limit.
- The FFB state can only be read after an exclusive acquire (`DIERR_NOTEXCLUSIVEACQUIRED`
  otherwise). Phase 2 will read it.
- EnumEffects lists all 12 standard effects. The known quirk (only sine works reliably among
  the periodic effects) will be checked in Phase 2.

## Input mapping (from `pacewheel monitor`)

Captured on 2026-10-17 with `monitor --raw --log`, in two sessions:
- Session A: steering and buttons; pedals and shifter not connected.
- Session B: pedals and shifter connected; each control operated in a fixed order, with
  pauses, so log timestamps can be matched to physical controls.

### Axes

| Control | DirectInput | Raw report 0x01 | Range seen |
| --- | --- | --- | --- |
| Steering | X | bytes 1-2, signed 16-bit | full lock both ways: 0..65535 (raw -32768..32767) |
| Throttle | Z | bytes 5-6 | 0..65535 |
| Brake | Rz | bytes 11-12 | 0..65535 |
| Clutch | Slider (S0) | bytes 13-14 | 0..65535 |
| unused | Y, Rx, Ry | | never moved (Y rests at 32767, Rx/Ry at 0) |

All three pedals rest at 0 and reach the full 65535 at the end of travel.

### POV and buttons

Raw report: byte 15 is the hat (1 = up … 8 = up-left, 0 = centered). Bytes 16-18 are
buttons B1-B24, LSB first.

| Physical control | DirectInput | Notes |
| --- | --- | --- |
| D-pad | POV 0 | up 0°, right 90°, down 180°, left 270°, diagonals 135° and 315° also seen |
| A | B1 | |
| B | B2 | |
| X | B3 | |
| Y | B4 | |
| LB, left paddle shifter | B5 (expected) | **never registered** in any session (see below) |
| RB, right paddle shifter | B6 | the paddle and RB report the same button |
| LT | B7 | digital button, not an axis |
| RT | B8 | digital button, not an axis |
| Back | B9 | |
| Start | B10 | |
| SL | B11 | |
| SR | B12 | |
| Mode | B13 | |
| Prog | none | sends no input report; probably handled by the firmware (programming / remap) |
| H-shifter gears 1-6 | B17-B22 | one button per gear; neutral = no button |
| H-shifter reverse | B23 | the 7th position in the sequence; assumes a 6+R shifter |
| unused | B14-B16, B24 | never seen |

How the buttons were matched: the user pressed the buttons in the order LB, LT, SL, Back,
Mode, Prog, Start, SR, RT, RB, X, Y, B, A, left paddle, right paddle. The log has 13 button
events for those 16 presses. The long pauses in the log (about 8-16 s) sit exactly where LB,
Prog and the left paddle should be. The result is the standard Xbox-style numbering (A=1,
B=2, X=3, Y=4, RB=6, LT=7, RT=8, Back=9, Start=10, SL=11, SR=12, Mode=13), which supports
the alignment.

Open questions:
- **B5 (LB / left paddle) never fires.** It might be a hardware fault, a firmware remap done
  through the mobile app, or the button might only work in another mode. Worth checking with
  the joystick dialog (`joy.cpl`) before blaming this tool.
- Shifter: confirm it is 6+R (B23 = reverse) and not 7 forward gears.
- Raw X reached -32768, one below the declared logical minimum of -32767.

### Raw input report 0x01 at rest (MI_00, from `monitor --raw`)

```
01 47 00 00 80 00 00 00 00 00 00 00 00 00 00 00 00 00 00 F9 07
ID |X    |Y    |Z    |Rx   |Ry   |Rz   |Sl   |hat|buttons |pad  |
```

- X = 0x0047 (signed 71), which matches DirectInput's 32838 (= 32767 + 71).
- Y = 0x8000. Z, Rx, Ry, Rz and Slider are 0. Hat = 0, which is outside the declared 1..8
  range, so it reads as centered.
- **The two trailing bytes, declared as constant padding, carry a live 16-bit value.** At rest
  it drifted slowly from 0x07FF to 0x07F9 over about 90 s (values seen: 07FF, 07FE…07F9). The
  wheel sends a new report every time it changes, even with nothing touched, roughly 3 reports
  per second. About 15 minutes later it was 0x07C9-0x07D9, so it keeps falling slowly while
  the wheel is powered, which fits a warming temperature sensor. Because the descriptor marks these bits as constant, DirectInput and games
  ignore them. It looks like an undeclared sensor reading, perhaps motor temperature or current,
  or a raw centering sensor. Phase 4 can check whether it reacts to force feedback load.
